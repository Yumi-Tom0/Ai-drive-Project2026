# TODOアプリ 要件定義書

ファイルパス: `docs/todo/01_requirements.md`

## 1 目的と完成条件

本ドキュメントは、既存のExpress＋TypeScript＋EJSアプリケーションに追加するTODO管理機能の要件を定義します。

開発の完成条件は、REQ-01〜REQ-04の各機能が受け入れ条件を満たして正しく動作し、Neon SQL Editorでのテーブル作成手順と `sql/README.md` への記録が完了していること、およびVercelのPreview・Production両環境で期待通りに動作することです。

## 2 対象範囲と共通の前提

対象範囲は `/todo` 画面および REST API (`/api/v1/todos`) です。既存の `/` および `/api/db-check` はそのまま維持します。V1ではユーザー認証、優先度設定、絞り込み、タイトル更新機能は含めません。

既存のDB接続処理と `DATABASE_URL` をそのまま使用します。VercelのPreview環境とProduction環境は同一のNeon DBを参照します。認証なしの公開URLで動作するため、個人情報や重要データは扱わず、架空のデータのみを使用します。

## 3 機能要件

### REQ-01 一覧取得
* **操作**: TODO一覧を取得・表示します。
* **入力**: なし (`GET /api/v1/todos`)
* **結果**: 登録されているTODOの一覧データを取得します。0件の場合は空配列を取得します。
* **エラー**: DB不通等の場合に500/503エラーとなります。
* **受け入れ条件**: ステータス200で `{"status":"success","data":[...]}` 形式のレスポンスが返ること。0件の場合は `data` が `[]` であること。
* **確認方法**: `/todo` 画面アクセス時および一覧取得処理時にDevToolsのネットワークタブでレスポンスを確認します。

### REQ-02 登録
* **操作**: 新しいTODOを登録します。
* **入力**: `title`（文字列、前後の空白を除いて1〜100文字）
* **結果**: 新規TODOが追加され、`isCompleted` は `false` で作成されます。
* **エラー**: 入力欠落や型違いは400、空白のみまたは101文字以上は422エラーとなります。
* **受け入れ条件**: ステータス201で `{"status":"success","data":{...}}` が返り、前後の空白が除去されたタイトルで登録されること。
* **確認方法**: 登録フォームからタイトルを入力・送信し、画面一覧およびDBに反映されることを確認します。

### REQ-03 完了状態の部分更新
* **操作**: TODOの完了/未完了状態を更新します。
* **入力**: パスパラメータ `id`（1以上の整数）、リクエスト本文 `isCompleted`（ブーリアン値）
* **結果**: 対象TODOの完了状態が更新されます。
* **エラー**: 不正なID形式や型違いは400、存在しないIDは404エラーとなります。
* **受け入れ条件**: ステータス200で `{"status":"success","data":{...}}` が返り、更新後のTODOオブジェクトが取得できること。
* **確認方法**: チェックボックス等の操作により `PATCH /api/v1/todos/:id` を呼び出し、状態が変更されることを確認します。

### REQ-04 削除
* **操作**: 指定したTODOを削除します。
* **入力**: パスパラメータ `id`（1以上の整数）
* **結果**: 対象TODOがDBおよび画面から消去されます。
* **エラー**: 不正なID形式は400、存在しないIDは404エラーとなります。
* **受け入れ条件**: ステータス204で本文なし（空）のレスポンスが返ること。
* **確認方法**: 削除操作を行い、`DELETE /api/v1/todos/:id` のレスポンスが204であり画面から対象要素が消えることを確認します。

## 4 画面とブラウザ側の要件

画面は `/todo` に配置します。ブラウザ側からはFetch APIを使用して非同期にAPIを操作します。

クライアント側のJavaScriptにおいてAPI呼び出し処理を `TodoApi` クラス（`list`, `create`, `update`, `delete`）へ分割して実装します。具体的なクラス構成や画面用JSファイルの配置場所は要確認とし、設計書で定義します。

## 5 データとAPIの共通仕様

データベースのテーブルは `todo_tasks` を使用し、列構成は `id` (INTEGER, 自動採番, PK)、`title` (TEXT, 必須, 1〜100文字)、`is_completed` (BOOLEAN, 必須, 初期値false)、`created_at` (TIMESTAMPTZ, 必須, 初期値NOW()) です。

REST APIは `/api/v1/todos` をエンドポイントとします。リクエスト・レスポンスのJSONフォーマットでは、DBの `is_completed` を `isCompleted` に、`created_at` を `createdAt` に変換します。成功時のJSON構造は `{"status":"success","data":...}` とし、DELETE成功時の204レスポンスは本文がないためJSON解析を行いません。具体的なルーティングファイルやAPIコントローラーの配置場所は要確認とし、設計書で決定します。

## 6 エラーとHTTPステータス

エラー時のレスポンス構造は `{"status":"error","code":"...","message":"...","details":[]}` に統一し、内部のSQLや接続文字列は含めません。

発生条件とステータスコードの対応は以下の通りです。
* **400 (BAD_REQUEST)**: JSON不正、`title` の欠落、型違い、1未満や非整数などの不正なID形式
* **422 (VALIDATION_ERROR)**: 前後空白除去後の `title` が空文字（空白のみ）、または101文字以上
* **404 (NOT_FOUND)**: 対象のIDが存在しない場合
* **500 (INTERNAL_ERROR)** / **503 (DB_UNAVAILABLE)**: サーバー内部エラーまたはDB利用不可

## 7 確認・提出条件

Neon SQL Editorにて `sql/todo/020_create_todo_tasks.sql` を手動実行し、実行結果を `sql/README.md`（ファイル名、対象、実行日、結果）に記録します。GitへのPushのみではSQLが実行されない点に留意します。同名テーブルが存在し構造が異なる場合は削除せず講師に確認します。

Vercelにデプロイ後、Preview環境およびProduction環境の両方で `/todo` にアクセスし、REQ-01〜REQ-04の全操作が正常に動作することをDevToolsおよび画面上で確認して提出とします。
